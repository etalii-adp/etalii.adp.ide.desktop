# Reference machines

The machines etalii.adp spec 030's performance criteria are measured on, and what was measured there ([research R12](https://github.com/etalii-adp/etalii.adp/blob/develop/specs/030-desktop-native-rust/research.md), tasks T090 and T091): SC-005 (the project list within 2 seconds of starting, a workspace of 5,000 files within 3 seconds of being opened), SC-006 (panning, zooming and dragging on a canvas of 1,000 elements and scrolling a table of 10,000 rows keep pace with the pointer), SC-007 (idle with a workspace of 5,000 files and three documents open, at most half the memory of the standalone host's process and its browser tab together) and SC-008 (a change made on disk by another program appears in the open view within 1 second).

## How to measure

Every input is generated by code, the same on every run ([benches/generated.rs](../benches/generated.rs)): a workspace of 5,000 files in ten areas of ten modules (Markdown, JSON, YAML, XML and plain text, a few hundred bytes each) and a dependency graph of 1,000 elements in a grid of 40 columns, each depending on the one below it. Everything is built optimised.

```bash
cargo bench -p adp-shell --bench startup     # SC-005: the program started, to its first frame on the screen
cargo bench -p adp-shell --bench workspace   # SC-005 and SC-008 in the headless window
cargo bench -p adp-shell --bench canvas      # SC-006: pan, zoom and drag on 1,000 elements
cargo test -p adp-shell --release --test table -- --nocapture   # SC-006: 10,000 rows scrolled (T066)
cargo bench -p adp-hierarchy --bench core    # SC-005 and SC-008: the core paths, with criterion
```

SC-007, by hand once per release (R12), on macOS, with the standalone host at its reference commit published beside it (the .NET 10 SDK and Node 22 or later; publishing builds the standalone host's client with `npm ci`):

```bash
# The standalone host at 8b6ccfc, published as its release is (the backend serving the client's production build).
git -C ../etalii.adp.ide.standalone worktree add ../standalone-8b6ccfc 8b6ccfc
dotnet publish ../standalone-8b6ccfc/src/backend/EtAlii.Adp.Backend.Service -c Release -o /tmp/adp-standalone
# The desktop host, its inputs kept for the standalone host.
ADP_MEMORY_WORKSPACE=/tmp/adp-memory cargo bench -p adp-shell --bench memory
# The standalone host and Chrome, on the same inputs.
node parity/memory/standalone.mjs --publish /tmp/adp-standalone --workspace /tmp/adp-memory/workspace
```

- **The start-up probe** ([benches/startup.rs](../benches/startup.rs)) starts the `adp-desktop` program as a person does, once without arguments (the project list) and once with the workspace on its command line, six times each, and times from the moment it was started to the moment its first frame was on the screen: the program reports that moment when `ADP_STARTUP_PROBE` names a file, and keeps its state where `ADP_STATE` says, so the person's own project list is not touched. The first start is reported apart: it is slower after a build or a wake. It opens a real window; without a screen it says it could not measure.
- **The headless window** ([benches/window.rs](../benches/window.rs)) is the shell the program runs, drawn in egui frames of 1280 by 800 and timed from a frame's input to its tessellated triangles, which is all of a frame the processor does; the graphics card's part is not in these numbers.
- **SC-006** ([benches/canvas.rs](../benches/canvas.rs)) fits the canvas to the window, so every element and relation is drawn in every frame, and pans (a left drag on the empty canvas), zooms (twenty notches of the wheel) and drags an element, each a second there and back at a frame a step. Each gesture is checked to have done what it does: the drawing moved with the pointer, the scale changed, the element followed the pointer and its new place was written. The criterion is a frame at 60 frames a second, 16.7 ms, at the 95th percentile.
- **SC-008** ([benches/workspace.rs](../benches/workspace.rs)) changes the open tab's file and adds a file to the workspace from outside the window, and times how long until a frame paints the change, with frames drawn when the window asks for them or the watcher wakes it, as eframe draws them, and at 60 frames a second, as while the pointer moves. Between changes the window is checked to wait for input, so a change it shows is one the watcher woke it for. The workspace is opened by the temporary folder's own name, which on macOS is through a link (`/var` to `/private/var`).
- **The core paths** ([benches/core.rs](../benches/core.rs), criterion): the workspace tree read from the 5,000 files, and a change on disk reaching the watcher.
- **SC-007** compares the memory of the two hosts, each started as a person starts it and left idle, at three points: the project list, the workspace of 5,000 files open, and the workspace open with three documents in tabs, a Markdown file (`area-00/module-00/item-0000.md`), a JSON file (`area-01/module-00/item-0001.json`) and the canvas of 1,000 elements (`generated.dgr`), opened in that order so the canvas is the active tab and drawn; the last is SC-007's point. Each point is left idle for 15 seconds (`ADP_MEMORY_SETTLE`, `--settle`) and then read five times a second apart, and the median is reported. Memory is the **physical footprint** that macOS's `footprint` reports per process (`phys_footprint`, what Activity Monitor shows as Memory), summed over the host's processes; the resident size `ps` reports (`rss`) is given beside it, but it counts the pages processes share once per process, which inflates Chrome's eight processes. [benches/memory.rs](../benches/memory.rs) writes the inputs of [benches/generated.rs](../benches/generated.rs) where `ADP_MEMORY_WORKSPACE` says, checks in the headless window that the command line it gives opens the workspace with the three tabs and the canvas drawn, then starts the release build of `adp-desktop` once per point with the workspace and the documents on its command line (`adp-desktop <folder> <file>...`), its state in a folder of its own (`ADP_STATE`), and reads its one process. [parity/memory/standalone.mjs](memory/standalone.mjs) (Node 22 or later, no packages) starts the standalone host's published backend (`dotnet EtAlii.Adp.Backend.Service.dll`, `Production`, on `127.0.0.1:5099`) with a temporary `HOME`, so the person's own ADP project list is neither read nor changed, and with a user name and credential it makes up for the run, starts Google Chrome with a temporary profile, one window of 1280 by 800 and one tab, and drives the page through Chrome's DevTools protocol as a person does: it signs in, adds the workspace as a project, opens it, expands the folders in the explorer and double-clicks the three documents, and checks that their tabs are open and that the canvas's last element is in the page. It reads the backend's process, and Chrome's browser process with every process under it (eight at the points measured, as Chrome starts them for one tab).
- **windows-latest**: the runner is measured by a `benchmarks` job in the Build workflow that runs the commands above on `windows-latest` only when the workflow is run by hand with a `benchmarks` input ticked (`if: github.event_name == 'workflow_dispatch' && inputs.benchmarks`, `continue-on-error: true`), writing what it measured to the run's summary, so no pull request or push waits for it. The job is not in the workflow yet: a change to a workflow needs a token allowed to change workflows, which the change that added these benchmarks did not have.

## Findings

- **SC-007 is met with room to spare**: idle with the workspace and three documents open, the desktop host's one process uses about 70 MiB, an eighth of the 560 MiB that the standalone host's backend and Chrome use together; it would meet the criterion against the standalone host's backend alone (165 MiB), without its browser. Most of the desktop host's memory at that point is the open canvas: the workspace without documents takes 27 MiB, the three documents open with the canvas not the active tab took 43 MiB in a run that opened the canvas first, and drawing the canvas of 1,000 elements as the active tab adds the rest. The comparison favours the standalone host where it can: Chrome ran with a fresh profile, one tab and no extensions, while a person's Chrome holds more, and its own browser, GPU and service processes, which a person's Chrome would share with their other tabs, are counted in full, as they are what the standalone host needs to run. Not measured: memory after use (panning, editing, undo), which a person's session reaches and which a script of the hosts' gestures would add; and the other platforms, as the probe reads memory with macOS's `footprint`.

- **Dragging an element on a canvas of 1,000 elements meets SC-006 since its frame draws again only what the drag moves**: it missed at first, a frame of the drag taking about 20 ms, about 50 frames a second, while a pan or a zoom of the same canvas took about 4 ms. A drag changes the scene in every frame, and every frame built it again from nothing: the layout and the placement of all 1,000 elements (about 4.5 ms), the scene's primitives for every element and line (about 6 ms), and what the gestures hit-test against, found with a search through every box drawn so far for each primitive and every text measured twice (about 5 ms). Now the scene is kept in pieces, one per line and per element (`adp_scene::scene::ScenePieces`), and a frame of a drag or a resize keeps what was placed, draws again only the elements whose box changed and the lines ending at them, and measures only those pieces for the hit tests, so a frame of the drag takes about 6.6 ms. The drop still takes about 67 ms, one frame, as it writes the file and builds the scene of the changed diagram from nothing. What is written is unchanged.
- **The window waits for input when nothing happens**: the shell sends the window's title to eframe only when it changes, as egui asks for a new frame whenever a viewport command is sent, and the watcher wakes the window when it hands over a change on disk, so SC-008 holds without the window drawing continuously.
- **A project opened through a link follows the disk in its tabs too**: the watcher may name changed files by their real path (on macOS, `/private/var` for `/var`), and the shell maps them back to the folder as it was opened, so the tabs, the explorer and the watcher name a file alike.
