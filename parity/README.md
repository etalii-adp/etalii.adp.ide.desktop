# Parity

What etalii.adp spec 030's FR-010, FR-032, SC-002 and SC-004 are checked against ([contracts/parity.md](https://github.com/etalii-adp/etalii.adp/blob/develop/specs/030-desktop-native-rust/contracts/parity.md)): the inventory of the standalone host's capabilities ([inventory.md](inventory.md)), the edit scripts ([scripts/](scripts/)), the documents they open ([fixtures/](fixtures/README.md)), the bytes the standalone host wrote for them ([goldens/](goldens/)) the program that recorded those bytes ([recorder/](recorder/README.md)), and the user stories walked by hand in the desktop host, with their screenshots ([walks.md](walks.md)). The machines the performance criteria SC-005 to SC-008 are measured on, and what was measured there, are in [reference-machine.md](reference-machine.md).

Every golden is the standalone host's bytes at spec 030's reference commit `8b6ccfc`, except those of a script folder whose `reference` file names a later commit: the Hierarchical Requirement Designer's are recorded at `a7fdf03` (etalii.adp spec 036, research R3; [recorder/README.md](recorder/README.md), "A second reference commit"). Each golden's `recorded.json` names its commit as `standaloneCommit`.

## The check

`cargo test -p adp-parity` replays every script headless in the desktop core and compares every file its golden lists byte for byte (task T050, `crates/adp-parity`). Per script it:

1. copies the fixture's folder into a temporary project, as the recorder does;
2. opens the registration (else the fixture) through `adp-diagram`'s `DiagramWorkspace`, and takes the session's baseline, as `DiagramService.Open` and `UpdateView` did;
3. maps each step onto the `DiagramSession` as the recorder mapped it onto the standalone host's RPCs: `select` sets the selection; `action` runs `execute` on `args.target` (an element, `new:x,y` the canvas, `rel:a->b` a finished connect gesture, `rel:a->new:x,y` one released on empty canvas, which runs `connect_to_new` with the first relation type that may leave `a`) or the selection, answers its prompt with `args.value`, or with `args.confirm` for a confirmation, and dismisses it otherwise; `property` finds the row by id or by its label and runs `set_property`; `move` runs `move_element` for a `parent`, else `move_elements` to `to` or to the element's place plus `dx` and `dy`; `undo` and `redo` run on the project's history; `save: true` sends nothing;
4. gives every element or connection a step creates the id the standalone host generated at that step, from `recorded.json`, and resolves `$N` and `$cN` to the N-th generated element and connection, so the bytes can match;
5. compares each file of the golden's `changed` list with the project's file of that path, and checks that each file of `removed` is gone.

A step the standalone host accepted and the desktop host refuses (or the other way round, for `"expect": "refused"`) is reported with the desktop host's sentence, and a file that differs is reported with its first differing byte offset and the line holding it in the golden and in the replay.

### A designer's script

A Knowledge designer script (`etalii/knowledge/*`, task T063) opens the registration through the module's `KnowledgeSession`, as `DesignerService.OpenTable` opened it, asks for the rows in sight, and maps each step as the recorder sent it ([recorder/README.md](recorder/README.md), "Tables"): `table` is the gesture, said in the view the connection shows unless it names one, written behind as the standalone host writes it; `view` sets the view the connection shows, which writes the view the file is left in; `undo` and `redo` are the session's, which is the project's history for these scripts, since every edit goes through the one session. An edit that makes something - a row, an option, a view - is handed the id the standalone host generated at that step, from `recorded.json`, and `$N` names the N-th of them.

### Line endings

A golden is the standalone host's bytes on the platform `recorded.json` names (every golden here was recorded on `windows`). The C4 layout sidecar (`*.layout.json`) and the Wardley map's identity sidecar (`*.identities.json`) are the two files the standalone host writes with the platform's line ending, `System.Text.Json`'s indented output using `Environment.NewLine` ([recorder/README.md](recorder/README.md)), so the check compares them in the line endings of the platform the golden was recorded on: on another platform, the replay's sidecar has its line endings turned into the recorded platform's (CRLF for `windows`) before the comparison. Every other file, and a sidecar on the recorded platform, is compared exactly as written: `roadmap.tml` is CRLF because its fixture is, not because of the platform.

### A script that does not match yet

Every script is a test in `crates/adp-parity/tests/parity.rs`. A script whose tool type cannot open yet in the desktop host, or whose bytes do not match yet, stays a test, ignored with its concrete reason, and its row below says so. `cargo test -p adp-parity -- --ignored` replays them all and prints what differs. The goldens and the scripts are never changed to make a replay pass: when one matches, its `#[ignore]` goes and its row says `matches`.
